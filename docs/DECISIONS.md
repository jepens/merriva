## #11 — 2026-07-24 · Fondasi DB & RLS pada migrasi v1
**Keputusan:** RLS aktif di 12 tabel; `service_role` (server) bypass RLS tanpa policy; admin dibedakan lewat `public.is_admin()` (SECURITY DEFINER, anti-rekursi ke RLS `profiles`), kepemilikan tabel anak lewat `public.owns_invitation()`. Trigger `handle_new_user` membuat baris `profiles` otomatis saat register; trigger `set_updated_at` untuk `invitations` & `rsvps`. Enum Postgres untuk himpunan literal tetap; `packages.code` tetap `text`. Seed `packages` ditaruh **di dalam migrasi** (idempoten `on conflict do nothing`), bukan `seed.sql`.
**Alasan:** pola standar Supabase; mencegah chicken-egg RLS pada `profiles`; `packages` adalah config esensial yang wajib ada di semua environment (ikut `supabase db push`, sementara `seed.sql` hanya jalan pada `db reset` lokal).
**Ditolak:** text+CHECK untuk semua status (dipilih enum demi integritas); seed packages hanya di `seed.sql` (tidak terbawa ke staging/prod).
**Konsekuensi:** fungsi `language sql` yang mereferensikan tabel harus didefinisikan **setelah** tabelnya (body di-parse-check saat CREATE).

## #12 — 2026-07-24 · Health check `/api/health` = probe reachability Supabase
**Keputusan:** `/api/health` mengembalikan `{status, db, uptime, timestamp}`; `db` diperoleh dari probe HTTP ringan ke endpoint REST Supabase (schema-agnostic, timeout 2,5 dtk). HTTP **200** bila `up`/`not_configured`, **503** bila `down`. Dipakai Docker `HEALTHCHECK` + UptimeRobot.
**Alasan:** cek reachability tanpa mengikat skema tertentu; `not_configured` → 200 agar container tetap dianggap hidup di lingkungan tanpa env DB (build/CI).

## #13 — 2026-07-24 · Model privilege DB eksplisit + hardening kolom (pasca-audit adversarial)
**Keputusan:** Migrasi v1 memberi GRANT privilege objek EKSPLISIT ke peran Supabase (service_role `ALL`; authenticated `SELECT/INSERT/UPDATE/DELETE`; anon `SELECT` katalog saja) plus `ALTER DEFAULT PRIVILEGES` untuk objek migrasi berikutnya — tidak bergantung pada konfigurasi default-privileges environment. Di ATAS RLS, kolom sensitif dikunci di level privilege: client tidak bisa `UPDATE` `profiles.role` (anti-eskalasi admin), `invitations.status/active_until/package_id/published_at` (anti-aktivasi tanpa bayar), maupun kolom data `rsvps` selain `is_hidden/is_approved`. Kolom terkunci hanya ditulis service_role (server action).
**Alasan:** temuan audit adversarial M0 — (a) tanpa GRANT eksplisit, RLS jadi moot & seluruh query DB gagal `permission denied` saat deploy (RLS hanya jalan bila peran punya privilege objek); (b) RLS membatasi BARIS, bukan KOLOM, sehingga policy "UPDATE baris sendiri" membuka eskalasi privilege & bypass pembayaran. Semua diverifikasi fungsional di Postgres lokal (`has_column_privilege` + uji akses per-peran).
**Konsekuensi:** setiap migrasi baru dengan tabel/kolom sensitif WAJIB menyertakan grant + (bila perlu) hardening kolom; mutasi kolom terkunci HARUS lewat server action service_role.

## #14 — 2026-07-24 · Hardening advisor + migrasi remote via Supabase MCP
**Keputusan:** Migrasi v2 (`harden_functions`) memindah fungsi helper RLS (`is_admin`, `owns_invitation`) ke skema `private` (tak diekspos PostgREST) dan mencabut `EXECUTE` fungsi trigger (`set_updated_at`, `handle_new_user`) dari peran API + mengunci `search_path` `set_updated_at`. Project remote staging (`ophmeifbjsffxklbeqla`) dimigrasikan lewat **Supabase MCP** (`apply_migration`); versi remote `20260724182301_init_schema` & `20260724182817_harden_functions`, dan nama file lokal disamakan agar `supabase db push` konsisten.
**Alasan:** menutup 7 lint advisor Supabase tanpa memutus policy/trigger — `ALTER FUNCTION ... SET SCHEMA` menjaga referensi via OID sehingga policy tetap valid. Diverifikasi: `get_advisors` bersih + `anon` tetap bisa membaca `packages` (policy memanggil `private.is_admin()`).
**Konsekuensi:** helper RLS dipanggil sebagai `private.*` di policy mendatang; peran perlu `USAGE` pada skema `private`. MCP `apply_migration` memakai timestamp versinya sendiri — samakan nama file lokal dengan versi remote saat memakai keduanya.

## #15 — 2026-07-25 · M1.1 Autentikasi: Server Actions native + Supabase SSR (PKCE)
**Keputusan:** Modul auth (register + verifikasi email, login, Google OAuth, reset kata sandi, profil, shell dashboard) dibangun dengan **Server Actions native + `useActionState`** (tanpa react-hook-form) mengikuti alur `@supabase/ssr`: verifikasi email & recovery lewat route `/auth/confirm` (`verifyOtp` dengan `token_hash`), OAuth Google lewat `/auth/callback` (`exchangeCodeForSession`, PKCE). Validasi diulang di server dengan skema Zod (`src/lib/validation/auth.ts`). Parameter `next`/redirect disanitasi (`safeNextPath`) untuk mencegah open-redirect. UI primitives shadcn (button/input/label/card/alert) ditulis manual **tanpa Radix** (tanpa dependency baru). Nomor WA dinormalisasi ke E.164 (`src/lib/phone.ts`). Tipe DB **digenerate** dari skema remote (`src/types/database.ts`) dan generic `Database` dipasang ke seluruh client Supabase.
**Alasan:** form auth sederhana → `useActionState` + progressive enhancement sudah cukup dan menghindari dependency; react-hook-form disiapkan untuk **editor multi-step M1.3** (butuh `useFieldArray` untuk list dinamis). Pesan generik pada signup & reset → cegah enumerasi email. Eskalasi role tetap tertutup (trigger `handle_new_user` hanya mengisi `full_name`/`phone`; hardening kolom v1 §6b). Generate tipe DB memutus ketergantungan pada `any` dan menyelaraskan query dengan skema.
**Ditolak:** react-hook-form untuk form auth (belum perlu di M1.1); template email default `{{ .ConfirmationURL }}` (dipilih `{{ .TokenHash }}` → route SSR agar sesi ditaruh server-side).
**Konsekuensi (WAJIB dikonfigurasi pemilik di Supabase Auth — lihat `docs/AUTH-SETUP.md`):** (1) **Site URL** = `${NEXT_PUBLIC_APP_URL}` dan **Redirect URLs** memuat `${APP_URL}/auth/callback` & `${APP_URL}/auth/confirm`; (2) **template email** Confirm signup & Reset password memakai format `{{ .TokenHash }}` menuju `/auth/confirm`; (3) aktifkan **provider Google** (client id/secret) bila OAuth dipakai. Regenerasi `src/types/database.ts` setiap ada migrasi baru.
**Review keamanan (adversarial, 4 lensa) — diperbaiki:** (a) `safeNextPath` bisa di-bypass karakter kontrol (TAB/LF/CR) & backslash yang dibuang/dinormalkan parser URL → kini menolak semua kontrol C0/DEL + backslash, dengan uji regresi; (b) proteksi enumerasi email pada signup dibuat **self-contained** (email sudah terdaftar → respons sukses identik, tak bergantung pada toggle "Confirm email"), plus `enable_confirmations=true` di `supabase/config.toml`. **Ditunda ke M2 (terjadwal roadmap):** rate-limit + Turnstile pada endpoint auth (interim: rate-limit bawaan Supabase `[auth.rate_limit]`). Lensa privilege/RLS: **nihil temuan** (hardening kolom v1 tahan).

## #16 — 2026-07-25 · Model konten undangan (M1.2): `content` JSONB per kategori + kontrak tema
**Keputusan:** `invitations.content` divalidasi Zod sebagai **discriminated union** pada `category` (wedding/corporate/family) di `src/lib/validation/content/`. Pembagian penyimpanan mengikuti DATA-MODEL: **jadwal** ternormalisasi di `invitation_events` (fondasi check-in Fase 2, skema `event.ts`), **galeri** di tabel `media`, **slug/tanggal utama** di kolom `invitations` — sisanya (deskripsi pihak, cerita/agenda/doa, amplop, sapaan, kutipan, embed YouTube, livestream) di `content`; perilaku & tampilan (varian tema, toggle section, moderasi ucapan, **timezone acara**, lagu latar) di `settings`. Foto bernama (cover/mempelai/logo) disimpan sebagai **`storage_path` relatif** di content (bukan URL vendor). Kontrak props tema **`InvitationData`** (`src/types/invitation.ts`) memuat content + settings + events + media + music(resolved) + watermark — tema **DILARANG** fetch; personalisasi tamu disuntik client (M2). Section dianggap tampil kecuali di-set `false`. Slug punya `slugSchema` + blocklist rute sistem/kata terlarang + `normalizeSlug`.
**Alasan:** JSONB fleksibel per kategori (SPEC §4.4) + normalisasi untuk data yang di-query/agregasi (DATA-MODEL). Discriminated union memberi validasi + tipe per kategori dari satu sumber. Timezone di `settings` karena `invitation_events` tak punya kolom TZ (CLAUDE.md: UTC → tampil WIB/WITA/WIT).
**Ditolak:** menaruh jadwal/galeri di `content` (melanggar normalisasi); menyimpan URL vendor (boundary §11/§6.4); kolom TZ baru di DB (pakai settings JSONB).
**Konsekuensi:** menambah field konten = ubah skema kategori terkait; bila berdampak render → ubah `InvitationData` = **"tanya dulu"**. Draft awal (`emptyContent`) sengaja belum lolos validasi penuh (field wajib kosong) — validasi penuh saat preview/aktivasi. Livestream & embed YouTube = Premium (tier ditegakkan server, M1.6). **Review faithfulness (3 lensa) — nihil field SPEC yang hilang**; diperbaiki 2 temuan low: `storagePathSchema` kini bentuk-positif (tolak `//host`, `\`, traversal `..`), dan default `envelope` jadi factory (cegah aliasing array antar-parse).

## #17 — 2026-07-25 · Editor form: react-hook-form + zodResolver (hybrid Server Actions)
**Keputusan:** Editor multi-step (M1.3) memakai **react-hook-form** (`^7.82`) + **@hookform/resolvers** (`^5.4`, `zodResolver`) untuk state form client, validasi per-field yang **me-reuse skema Zod M1.2**, dan list dinamis via **`useFieldArray`** (sesi acara, rekening, e-wallet, entri cerita). Owner mendelegasikan keputusan ke best-practice hasil riset.

## #18 — 2026-07-25 · M1.3a: tutup bypass INSERT invitations + alur buat draft
**Keputusan:** Migrasi **v4** menutup lubang bypass pembayaran yang ditemukan saat M1.3: `authenticated` bisa `INSERT` kolom `status/active_until/package_id` → self-activation tanpa bayar (migrasi v1 §6b hanya mengeraskan UPDATE). Diperbaiki: cabut INSERT tabel-level + grant ULANG hanya kolom aman (`user_id, theme_id, slug, category, content, settings, event_date`) — analog hardening UPDATE. Migrasi **v3** seed metadata tema pertama (`eternal-rose`, wedding/standard). Alur buat draft: `createInvitationAction` (auth → validasi Zod → cek tema mendukung kategori → INSERT draft `status` default `draft` → redirect editor); slug awal sementara `draft-…` (pemilik menetapkan slug asli di editor). Halaman pilih kategori+tema pakai **react-hook-form** (pemakaian RHF pertama).
**Alasan:** melengkapi model privilege #13 yang melewatkan INSERT; `status`/lifecycle hanya boleh ditulis service_role (pembayaran). Diverifikasi di remote: `has_column_privilege('authenticated','public.invitations','status','INSERT')` = **false**, service_role = **true**; theme seeded.
**Konsekuensi:** membuat undangan hanya untuk kategori dengan tema aktif (kini wedding/`eternal-rose`; corporate/family menunggu tema tambahan M4). Slug asli + form per-langkah + autosave = M1.3b–d. Setiap tabel baru dengan kolom sensitif WAJIB mengeraskan INSERT **dan** UPDATE.

## #19 — 2026-07-25 · Editor M1.3b: arsitektur draft + autosave
**Keputusan:** Editor **per-kategori konkret** (mulai `WeddingEditor`), bukan satu editor generik di atas union `content` — menghindari friksi tipe `register` RHF pada union. **Autosave berbasis perubahan** (`useDraftAutosave`: subscribe RHF → debounce 800ms → `saveInvitationDraftAction`). Persistensi draft memakai **skema draft longgar** (`draftContentSchema`: field wajib direlaksasi menjadi opsional, TAPI batas panjang, format `storage_path`/URL/YouTube, dan batas jumlah array TETAP ditegakkan); validasi **strict penuh** hanya saat preview/aktivasi. Server menyimpan **hasil parse** (unknown key ter-strip Zod), bukan input mentah client. Primitif `Input`/`Textarea` diubah ke `ComponentProps<...>` agar `ref` dari `register` diteruskan (React 19, tanpa `forwardRef`). Slug tetap sementara `draft-…` (edit slug + cek ketersediaan real-time = M1.3d).
**Alasan:** union `content` menyulitkan path `register`; editor per-kategori memberi tipe konkret & UX terarah. Draft schema memungkinkan simpan bertahap tanpa mengorbankan keamanan/ukuran JSONB. Menyimpan hasil parse mencegah injeksi key liar & membatasi payload.
**Konsekuensi:** tiap kategori punya editor sendiri (corporate/family menyusul saat temanya ada, M4). Langkah 2–7 wedding (mempelai, jadwal, galeri, cerita, amplop, pengaturan) = M1.3c; autosave sudah aktif untuk field yang tersedia. Warning ESLint `react-hooks/incompatible-library` (React Compiler tak memoize RHF) diketahui & tidak menggagalkan lint.

## #20 — 2026-07-25 · M1.3c-2 Jadwal: events ternormalisasi + RPC atomik + konversi timezone
**Keputusan:** Langkah "Jadwal" mengisi `invitation_events` (ternormalisasi — fondasi check-in Fase 2). Bar proyek = 0 lint. Admin client server-only tak terekspos ke REST → permukaan serang lebih kecil, cek hanya lewat server action (auth+kepemilikan+TODO rate-limit), dan tanpa migrasi. **Ditolak:** (a) fungsi `SECURITY DEFINER` di `public` — kena advisor WARN & terekspos REST; (b) memindah ke schema `private` — tak bisa dipanggil `.rpc()` (PostgREST hanya expose `public`); (c) slug bisa diubah kapan saja — mengubah alamat undangan aktif memutus tautan WA yang tersebar → dikunci ke `status='draft'`.

Cek ketersediaan bukan endpoint form → tak pakai `ActionState`, melainkan tipe hasil sendiri (`SlugCheckResult`/`SlugSaveResult`). TODO(M2): rate-limit `checkSlugAvailabilityAction`.

**Alasan:** `insert_guest` sengaja dibuat M1.6 justru untuk titik ini (satu cek limit atomik, tak bisa di-override REST). Ubah/hapus tak butuh RPC (bukan operasi ber-limit) → tabel langsung via RLS = least-privilege & lebih sederhana. Menyimpan E.164 sejak input membuat generator wa.me M2.4 trivial (buang `+`) dan menyeragamkan data. Token server-side (bukan klien) supaya tak bisa dipilih tamu/penyerang. **Diverifikasi browser (stack lokal, owner login):** tambah (`0812-3456-789` → `+628123456789`, token 14 char di DB) → ubah-inline (nama+pax persist) → hapus (kuota kembali) → konsol bersih. Gate: typecheck 0, lint 0, **127 test** (+9), build `ƒ /…/tamu` & `/[slug]` tetap `○` ISR.
**Ditolak:** (a) tambah tamu via tabel langsung (lewati limit atomik `insert_guest` — RPC wajib untuk jalur ber-limit); (b) react-hook-form (form kecil; state ringan cukup & konsisten dgn form publik); (c) menyimpan phone apa adanya (E.164 menyeragamkan + siap wa.me); (d) mengizinkan edit `token` (identitas tamu/QR — memutus link tersebar); (e) grant kolom DB khusus `guests` (owner mengubah token miliknya sendiri = risiko rendah, tak lintas-tenant; dikontrol di action, dicatat sebagai TODO bila perlu pengetatan).
**Konsekuensi — M2.3b & M2.4:** **Impor Excel/CSV + ekspor** (SPEC §4.7 "impor 500 tamu <30 dtk", "ekspor ke Excel") = **M2.3b**, butuh keputusan dependency parser (boundary "tanya dulu") → RPC massal `insert_guests_bulk` (satu advisory lock + satu cek limit untuk seluruh batch, seperti diisyaratkan komentar migrasi M1.6).
